第 01 讲：Protobuf、JSON 与序列化

1.1 数据为什么要序列化？

假设 Python 程序有一个学生对象：

这个字典是 Python 进程中的对象，不能要求 Java、Go 或另一台服务器直接理解其内存结构。

因此，需要把对象转换成一串可以存储或传输的数据：

  • 序列化（Serialization）：把内存中的消息转换为字节序列。
  • 反序列化（Deserialization）：按照约定的结构，把字节恢复为消息对象。

JSON 是文本序列化格式，Protobuf（Protocol Buffers）则是一种带有结构定义的二进制序列化机制。

2.3 字段编号的规则

规则：

  1. 在同一个 message 中，字段编号必须唯一。
  2. 编号不能为 0，合法范围为 1 至 536870911，其中 19000 至 19999 是保留区间。
  3. 编号一旦随公开或持久化的数据投入使用，就不要修改或复用。
  4. 编号 1～15 的常见字段 Tag 编码通常只需要一个字节，因此可优先分配给高频字段。

不同的消息可以分别使用字段编号 1；这个编号并非整个项目范围内全局唯一。

第 06 讲：Schema 演进、reserved 和未知字段

分布式系统通常无法保证所有服务和移动客户端同时升级。旧客户端可能还在读取新服务端产生的数据；历史缓存、日志和消息队列中也可能保存旧结构数据。

因此，Schema 不仅要“当前能用”，还要“长期可演进”。

6.1 向后兼容与向前兼容

假设：

V1：

V2：

定义：

  • 向后兼容（Backward Compatibility）：新程序能够读取旧数据（V2 读 V1）。
  • 向前兼容（Forward Compatibility）：旧程序能够读取新数据中的已知内容（V1 读 V2）。

这仅说明相关二进制数据能够正确解析，并不保证新增的业务校验、权限与处理逻辑也兼容。

6.2 修改字段的风险表

变更 二进制层面 主要风险
增加新编号字段 通常 Wire-safe 老程序不认识新字段
将字段 2 改为 5 Wire-unsafe / 语义破坏 原字段变未知字段
删除字段，不再复用编号 通常可逐步演进 历史数据、业务代码要处理
复用已发布的编号 危险 旧数据被解释成新含义
更改字段名但保留编号与类型 二进制通常可兼容 API、JSON、反射受到影响
增加枚举值 二进制通常可容纳 旧程序必须正确处理未知枚举值
int32 改为 int64 有条件兼容 新数值可能超出旧范围
int64 改为 string 通常不兼容 Wire Type 与语义不同
修改 oneof 结构 需单独评估 字段互斥、清除、未知状态问题

不同变更可能是 Wire-safe、Wire-compatible（有条件安全）或 Wire-unsafe。 JSON 的兼容性规则不等同于二进制格式。

6.7 版本升级的实战流程

  1. 新增新编号字段，先保证未设置时的兼容行为。
  2. 让读取方逐步支持新字段，在旧客户端尚存时不要强行依赖它。
  3. 逐步升级写入方，必要时双写旧字段与新字段并定义权威来源。
  4. 验证历史数据、回滚、消息队列和服务混部。
  5. 退役旧字段后保留编号与名称，不要随意复用。

对于删除、类型调整、oneof 重构，不存在一个无条件适用的升级顺序。先写兼容矩阵和迁移方案，再进行灰度部署。

7.8 直接使用 TCP 时要注意什么？

Protobuf 负责消息编码，TCP 接收方还需要知道消息边界。可约定长度前缀：先读满 4 字节长度，再读满相应大小的 Payload，最后调用解析 API。一次 recv() 不保证返回全部数据，还要处理消息大小上限、断连和部分读取。gRPC 会提供消息分帧和远程调用机制。

8.1 RPC 与 Protobuf 的分工

  • RPC：Remote Procedure Call，远程过程调用。
  • Protobuf：定义请求/响应的数据结构，并对消息序列化。
  • gRPC：提供远程调用的 Stub、服务端框架、HTTP/2 传输、状态码、Deadline、流式通信等机制。

这意味着客户端可以写出类似调用本地方法的代码：

而实际发生的是请求序列化、网络发送、服务端执行、响应序列化和客户端解析。

8.2 .proto 的 service 与 rpc

除了 message，还可以声明：

  • service：远程服务。
  • rpc：一个远程方法。
  • 括号里的类型：请求消息。
  • returns (...)：响应消息。
  • 请求与响应必须是 Protobuf 消息类型（可以为空消息）。

8.3 gRPC 的四种通信模式

模式 请求 响应 .proto 写法
Unary 1 条 1 条 rpc Get(Req) returns (Resp);
Server Streaming 1 条 多条 rpc List(Req) returns (stream Resp);
Client Streaming 多条 1 条 rpc Upload(stream Req) returns (Resp);
Bidirectional Streaming 多条 多条 rpc Chat(stream Req) returns (stream Resp);

stream 表示 RPC 级别的消息流，不等同于单个 message 里面包含 repeated 列表。

本讲实现四个 RPC，覆盖两种通信模式：创建、查询和更新使用 Unary RPC，列表使用 Server Streaming。Client Streaming 与双向流留作扩展练习。

Java 的 withDeadlineAfter() 在每次 RPC 前设置新的截止时间。只在初始化 Stub 时设置一次并长期复用，会让后续调用继承不断减少甚至已经过期的时间预算。Python 则在每次调用中传入 timeout=5。

8.14 gRPC 进阶：生产化必须补上的能力

本章是教学版网络服务，不是开箱即用的生产架构。要上线时还应考虑：

  • 传输安全：TLS / mTLS、服务端身份校验。
  • 业务安全：认证、授权、细粒度资源权限。
  • 可靠性：Deadline、优雅关闭、重试策略、幂等性。
  • 运行状态：健康检查、指标、日志、链路追踪。
  • 维护性：Proto Schema 版本治理、兼容性测试、自动生成代码。
  • 规模化：负载均衡、服务发现、流控、容量与背压。
  • 数据层：数据库、事务和持久化；不要把样例内存字典直接当生产数据库。
